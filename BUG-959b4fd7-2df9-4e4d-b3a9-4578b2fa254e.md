# BUG: `_pane_output` returns the *previous* command's output — `baseline` was dropped

**Severity:** HIGH — a caller cannot tell a fresh result from the last command's
leftover output; a command that prints nothing returns the previous result.
**File:** `main_tdashboard.py` (`_pane_output`, `wait_pane_idle`)
**Status:** OPEN

## Symptom

`_pane_output` documents a `baseline` subtraction that does not exist any more:

```python
def _pane_output(pane):
    """Output of the job that just finished: the screen minus what was there.

    `baseline` is the pane's screen captured when the wait started. Everything
    up to and including the last line of that baseline is prior content (old
    output, the previous prompt); the command's echo and its output are what
    appeared after it.
    """
```

There is no `baseline` parameter (the function takes only `pane`), nothing
computes one, and the single call site is `return _pane_output(pane)`. So the
"minus what was there" subtraction never happens: the function returns the last
non-framing block on screen, which may be from any earlier command.

`grep -n baseline main_tdashboard.py` finds the name only inside that docstring.

## Exact reproduction

Three commands in one pane, in order:

```
$ cd ~/github/dashboard && source venv/bin/activate
$ python3 - <<'PY'
import libtmux, main_tdashboard as md
tmux = libtmux.Server()
s = tmux.new_session(session_name="bleed", window_name="w", attach=False)
p = s.windows[0].panes[0]
p.send_keys("echo FIRST_OUTPUT")
print("1st:", repr(md.wait_pane_idle(p, timeout=10)))
p.send_keys("echo SECOND_OUTPUT")
print("2nd:", repr(md.wait_pane_idle(p, timeout=10)))
p.send_keys("true")
print("3rd (true):", repr(md.wait_pane_idle(p, timeout=10)))
s.kill()
PY
1st: 'FIRST_OUTPUT'
2nd: 'SECOND_OUTPUT'
3rd (true): 'SECOND_OUTPUT'
```

The third call ran `true`, which prints nothing. It returned `'SECOND_OUTPUT'`
— the *previous* command's output. Every value here is a plausible string, so a
caller recording evidence logs stale data as if it were the result of `true`.

The same defect makes a silent command indistinguishable from a chatty one:

```
$ python3 -c '...  p.send_keys("true"); print(repr(md.wait_pane_idle(p, timeout=10)))'
'true'          # the echoed command line, not an empty result
```

Earlier in this series the same input returned `''`.

## Why it matters

This is the return value that callers quote as evidence. The failure is silent
and plausible: no exception, no empty string, just the wrong command's output.
It undoes the point of the earlier work, whose whole thesis was that returning
chrome (a prompt) instead of output misleads callers — returning the *previous*
result is the same class of error and harder to notice.

## Why the tests miss it

Every `WaitPaneIdle` case stands in a mock screen:

```python
main_tdashboard.compat.capture_pane = lambda pane, start=None, end=None: ["$ "]
```

A bare prompt is framing-only, so the expected value is `""` and the check
passes regardless of baseline handling. No test runs two real sequential
commands in a real pane and asserts the second result does not contain the
first.

## Suggested fix

Restore the subtraction the docstring describes: capture the screen when the
wait starts, diff against it when the job finishes, and return only what is new.
Then add two cases that would have caught this:

1. `echo FIRST; echo SECOND` → second call does not contain `FIRST`;
2. a silent command after a chatty one → returns `""`, not the old output.

`wait_pane_output(pane, inner_cmd)` (added in b1d3d30) frames the command with
markers and is unambiguous; the fix either reuses that framing inside
`_pane_output` or restores the baseline diff.

## Verified on

Linux, `tmux 3.7b`, `venv/bin/python` 3.13, dashboard at `f0305df`; both
reproductions run as written.
