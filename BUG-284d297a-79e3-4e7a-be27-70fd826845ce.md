# BUG-284d297a-79e3-4e7a-be27-70fd826845ce

A `spawn_*` that calls `wait_pane_idle` straight after `panes_from_list` still
returns before its command runs, because the pane's seed line has not been
submitted yet.

## Reproduced

Build from `4c2d3e0` (contains `63abf78`, which requires a busy sample before
accepting an idle one):

```python
def spawn_w():
    session = renew_session("w")
    panes_from_list(session, [f"cd {REPO} && set -o pipefail; gh run watch {RUN} --exit-status; ..."],
                    start_directory=REPO)
    pane = compat.active_pane(session)
    last = compat.wait_pane_idle(pane, timeout=3600)   # returns in ~0s
```

Non-interactive run:

```
$ tmux-dashboard scripts --session-file /tmp/waitrun.py
Starting spawn_w()
└─[%] cd /home/deadbeef/github/network-labs && set -o pipefail; gh run watch 43329348953 --exit-status; ...
```

`wait_pane_idle` returned immediately, and the pane shows the command sitting at
the prompt **unexecuted**. Sending one bare Enter by hand then runs it:

```
$ tmux send-keys -t w Enter
  * Run repository test suite      <- gh run watch output appears
```

## Why

`panes_from_list` -> `send_keys_to_pane` types the line with
`send_enter_last_row=True` but returns after a fixed `time_out_unchecked=0.1`
(`main_tdashboard.py:342`). The Enter can still be queued, unsubmitted, when
`wait_pane_idle` takes its first sample.

`63abf78` fixed the *other* half of this race (an idle sample is not accepted
until a busy one has been seen). That does not help here: the shell genuinely is
idle and will stay idle until the Enter is consumed, so "wait for busy" waits
forever on a line that never gets submitted. With a shorter caller timeout this
turns into `PaneBusy` instead.

So the two halves are:

1. a pane whose seed line was never submitted looks idle forever -> this bug;
2. a pane whose command has not started yet looks idle -> fixed by `63abf78`.

## Suggested fix

Make `send_keys_to_pane` confirm the last row was submitted before returning:
after `send_enter_last_row`, wait until the echoed line is no longer the last
line, or until `at_end()` is false, bounded by `time_out_unchecked`. A fixed
0.1 s cannot express "the shell has read the Enter".

`checked_cmd` already avoids this by sending its own line *and* an end marker;
the remaining gap is only for callers that use `panes_from_list` +
`wait_pane_idle`.

## Severity

Same failure shape as the defect fixed in `63abf78`: a long job is reported as
finished immediately, and the caller reads a tail with no result. Here it also
leaves the intended command unexecuted, so a later `Enter` starts it out of band.
